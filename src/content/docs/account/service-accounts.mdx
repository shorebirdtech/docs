A service account is an account that belongs to an organization instead of a
person. It holds one role in that organization, and its API keys do what that
role allows. Use one for CI, release scripts, and integrations, so they keep
working when the person who set them up leaves or changes roles, and so the
audit log can tell automation from people.

A [personal API key](/account/api-keys/) acts as you: it can do at most what
your own role allows, and it stops working if your account is deleted. Use a
personal key for your own scripts, and a service account for anything your team
depends on.

Service accounts and their keys are available on every plan. Signing in from
GitHub Actions without a stored key, with a [trust rule](/account/trust-rules/),
needs a Business or Enterprise plan.

## Who can manage service accounts

The organization's Admins and Owner can see, create, change, and delete its
service accounts, their keys, and their trust rules. Other members can't see
them.

A service account is not a member. It doesn't appear on the **Members** page,
and it belongs to its organization for as long as it exists.

## Create a service account

1. In the [Shorebird Console](https://console.shorebird.dev), open your
   organization's **Settings** and select **Service Accounts**.
2. Click **Create service account**.
3. Enter a name for what will use it, such as `GitHub Actions`.
4. Choose a [role](#choose-a-role) and an [expiration](#issue-and-revoke-keys)
   for its first key.
5. Click **Create**.

The console creates the account and its first API key. The key is shown once:
copy it into your CI platform's secrets manager, for example as
`SHOREBIRD_TOKEN`.

The account is shown everywhere, including the audit log, as its name followed
by `[bot]`, such as `GitHub Actions[bot]`.

To create one from the command line, use [`shorebird api`](/account/api/). The
ID it needs, `<project id>` below, is the number after `/orgs/` in the console's
address bar, and `shorebird account orgs` lists it too.

```sh
shorebird api -X POST organizations/<project id>/service-accounts \
  -f name=release -f role=developer
```

Creating an account this way doesn't issue a key. Note the `id` it prints and
[issue a key](#issue-and-revoke-keys) for it.

## Choose a role

A service account can hold one of four roles. Pick the narrowest one that does
the job:

- **Viewer**: sees apps, releases, patches, channels, and insights. Use it for
  dashboards and other read-only integrations.
- **Developer** (the default): can also create releases and patches, create
  channels, and promote and roll back patches. Use it for CI that ships releases
  and patches.
- **App Manager**: can also create, update, and delete apps. Use it when
  automation creates apps, for example by running `shorebird init`.
- **Auditor**: reads the organization's
  [audit log](https://docs.shorebird.dev/account/audit-logs/) and nothing else.
  Use it for a tool that exports the audit log, so that tool doesn't need an
  Admin's key.

Every plan offers all four roles to service accounts. A service account can't be
an Admin or Owner, so a leaked key can't manage members, billing, other service
accounts, or the organization itself.

To change the role, pick another one on the account in the console. The change
applies right away to every key the account holds and to every job signed in as
it. From the command line:

```sh
shorebird api -X PATCH organizations/<project id>/service-accounts/<service account id> \
  -f role=viewer
```

A service account's keys have no permission level of their own. To give one
pipeline less access than another, create a separate service account with a
narrower role.

## Issue and revoke keys

Issue more than one key to rotate them without downtime: issue a new key, update
your CI secret, then revoke the old one. Every key acts as the same account, so
the audit history stays in one place.

To issue a key, click **Issue key** on the account, enter a name, and choose an
expiration: 30 days, 90 days, 1 year (the default), or never. A key that never
expires works until someone revokes it, so prefer an expiration, or
[sign in with a trust rule](/account/trust-rules/) where you can.

To revoke a key, open its options menu and click **Delete**. Requests using it
fail right away, and this can't be undone.

The same from the command line. Leave out `expires_in_days` for a 1-year key, or
pass `-F expires_in_days=null` for one that never expires. The key is in the
`api_key` field of the response, and it is shown only once.

```sh
# Issue a key that expires in 90 days
shorebird api -X POST organizations/<project id>/service-accounts/<service account id>/keys \
  -f name=github-actions -F expires_in_days=90

# List the account's keys
shorebird api organizations/<project id>/service-accounts/<service account id>/keys

# Revoke a key
shorebird api -X DELETE organizations/<project id>/service-accounts/<service account id>/keys/<key id>
```

## Use a key from CI or a script

The Shorebird CLI reads a key from the `SHOREBIRD_TOKEN` environment variable,
the same way it reads a personal API key:

```sh
export SHOREBIRD_TOKEN="<service account key>"
shorebird patch android
```

To call the [Shorebird API](/account/api/) directly, send the key as a bearer
token:

```sh
curl -H "Authorization: Bearer $SHOREBIRD_TOKEN" https://api.shorebird.dev/api/v1/apps
```

See [Running in CI and scripts](/code-push/ci/scripting/) for running the CLI
unattended, and the CI guides for [GitHub Actions](/code-push/ci/github/),
[Codemagic](/code-push/ci/codemagic/), and
[other CI systems](/code-push/ci/generic/).

A service account can do what its role allows on every app in its organization.
Requests about a person, such as account details, plan and billing, usage, and
invitations, are refused with `service_account_forbidden`, and so is creating an
organization.

## Sign in from GitHub Actions without a key

A GitHub Actions workflow can sign in as a service account with no stored key,
through a [trust rule](/account/trust-rules/) on that account. Trust rules need
a Business or Enterprise plan.

## Delete a service account

Click the trash icon on the account and confirm. Deleting it revokes all its
keys and deletes its trust rules, so anything using them loses access right
away. Its apps, releases, and patches belong to the organization and are not
affected, and its entries in the audit log stay.

```sh
shorebird api -X DELETE organizations/<project id>/service-accounts/<service account id>
```

## Service accounts in the audit log

The [audit log](https://docs.shorebird.dev/account/audit-logs/) records each
service account's actions with the account, `name[bot]`, as the actor, along
with the key or trust rule it used.
